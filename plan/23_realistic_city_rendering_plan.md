# 写実寄り街生成・道路レンダリング再設計計画

## 目的

`plan/real_map.png` のような、幹線道路と生活道路が階層的に混ざる日本の地方都市/郊外を、ゲーム本体の汎用システムとして生成・描画する。Test専用、スクリーンショット専用、特定シード専用の処理は禁止する。

## 現状の根本問題

1. 通常道路にも `kRoadSurfaceLift = 2.0` が効き、道路・標示・道路家具が地面から浮く。
2. 電柱、側溝、縁石、小看板などを `RoadRenderer::buildStreetFurnitureBatches()` で後付けしており、RoadPart としての所有関係、交差点処理、キャッシュ無効化が統一されていない。
3. 停止線、横断歩道、車線線、矢印が別々のキャッシュ/関数で生成され、道路標示の幅制限・向き・交差点との関係が統一されていない。
4. 建物配置は道路沿いスロットを使うが、道路フットプリントと敷地フットプリントの衝突判定が弱く、接道義務を「全土地の生成規則」として扱っていない。
5. 地表表現がゾーンセル単位のタイルに寄っており、地面テクスチャと土地ポリゴンが分離されていない。
6. 海岸の扱いが水面/地形の連続だけで、砂浜・護岸・セットバックが土地利用規則に入っていない。
7. 建物・道路素材が手続き箱中心で、写実寄りのテクスチャ/モデル資産を活用していない。

## アーキテクチャ方針

### A. RoadPart 物理断面の拡張

`RoadPartType` に以下を追加する。

- `UtilityPole`: 電柱・街灯柱など、道路に沿って長手方向に一定間隔で配置する部品
- `RoadsideGutter`: 開渠/暗渠側溝。既存 `Gutter` を幅方向面として残し、縁石横の立体側溝はこの部品で扱う
- `RoadsideObject`: カーブミラー、自販機、小看板、バス停など、道路付属物の基底型

既存の `RoadPart` は幅方向帯を前提にしているため、`RoadPart` 本体に `placement` と `envelopeRole` を追加する。長手方向配置の既定値やモデル情報は `RoadPartDef` に持たせるが、地形・区画・検証が registry なしで判定できるよう、構造幅に含めるかどうかは `RoadPart` 本体が canonical に持つ。

- `placement = Strip | RepeatAlongEdge`
- `envelopeRole = Structural | RoadOwnedObject`
- `spacing_m`
- `jitter_m`
- `side_policy = Left | Right | Both`
- `face = Tangent | RoadCenter | TravelDirection`

`placement` と `envelopeRole` は `RoadPart` 本体に保存する。`spacing_m` / `jitter_m` / `side_policy` / `face` は `defId` で参照する `RoadPartDef` の既定値として保存し、個別上書きが必要になった時点で別の `defId` を作る。

`RoadRenderer::buildStreetFurnitureBatches()` は廃止し、道路沿い設備は `buildPartMeshes()` から `RoadPart::placement` に従って生成する。これにより、電柱や側溝は道路断面・道路種別・交差点カットオフ・LODと同じライフサイクルで管理される。ただし UtilityPole などの `RoadOwnedObject` は道路所有物であっても構造幅・地形切削・Parcel exclusion には含めない。

生活道路は外側の `Slope` を持たない。断面は原則として以下にする。

```text
RoadsideGutter | Curb | Roadbed | Curb | RoadsideGutter
```

幹線道路は歩道・縁石・側溝を持つ。

```text
Sidewalk | RoadsideGutter | Curb | Roadbed | Curb | RoadsideGutter | Sidewalk
```

高速/有料道路だけが `Slope` / `Guardrail` を通常断面に持つ。

### B. 路面高さの統一

通常道路の地表からの浮きは `0.04m` 程度に統一する。

- `kRoadSurfaceLift`: 通常道路面のZファイト回避用微小リフトへ変更
- `kRoadLineLift`: 道路面 + 0.012m
- 高架/橋梁は `edge.useElevation == true` のときだけベジェYを使う
- 地形 subtraction は道路面に合わせて浅く行い、道路と地形の段差を作らない

### C. RoadMarking 統一システム

`RoadTypes.hpp` に `RoadMarkingKind` と `RoadMarkingPlacement` を追加する。

```cpp
enum class RoadMarkingKind : uint8
{
    LaneLine,
    StopLine,
    Crosswalk,
    DirectionArrow,
    KeepOut,
    ZebraZone,
};

struct RoadMarkingPlacement
{
    RoadMarkingKind kind;
    int edgeId;
    int nodeEndId;
    float arcOffset;
    float lateralCenter;
    float width;
    float length;
    float angleOffset;
    bool autoGenerated;
};
```

`RoadMarkingGenerator` を新設し、以下を一括生成する。

- エッジ上の車線区画線
- ノード手前の停止線
- 横断歩道
- 進行方向矢印
- 導流帯/ゼブラ

`RoadRenderer` は `buildRoadMarkingBatches(edge/node)` だけを呼ぶ。横断歩道もこの一種にする。

横断歩道の向きは「車道を横断する向き」、つまり道路接線に対して直交方向へ長く伸びる。ゼブラの各白帯は道路接線方向に細く、道路幅方向へ長い。既存実装は白帯生成軸が逆なので、`right` 方向を長辺、`tangent` 方向を帯間隔にする。

道路標示は必ず Roadbed の内側にクリップする。描画幅は `roadbedPart.offsetL/R` から得た車道幅を基準にし、`Curb/Gutter/Sidewalk` へはみ出さない。

### D. 接道義務を前提にした土地生成

建物セルを直接ランダム配置せず、道路から生成する `Parcel` を導入する。

```cpp
struct Parcel
{
    int id;
    ZoneType zone;
    Polygon footprint;
    int frontageEdgeId;
    float frontageStart;
    float frontageEnd;
    float setback;
    BuildingType buildingType;
};
```

生成規則:

- すべての宅地・商業地・工業地 Parcel は `frontageEdgeId` を持つ
- 生活道路沿いは小さい短冊状宅地、幹線沿いは大きめの店舗/駐車場 Parcel
- Parcel footprint と道路フットプリントは必ず分離し、建物は Parcel 内の setback 後方に置く
- 道路と建物の重なりは、配置時に道路フットプリントSDFまたは最近傍道路投影で拒否する
- 農地・田んぼも農道/生活道路に接する Polygon LandPatch として生成する

### E. 地表テクスチャと土地ポリゴンの分離

`WorldRenderer` の地形メッシュは、広域地表テクスチャを持つ TerrainLayer とする。

- grass
- soil
- sand
- asphalt
- gravel
- beach
- wet_paddy

その上に任意多角形の `LandPatch` を重ねる。

```cpp
enum class LandPatchType : uint8
{
    ParcelAsphalt,
    ParcelGravel,
    GardenSoil,
    FarmField,
    PaddyField,
    Beach,
    Seawall,
};

struct LandPatch
{
    LandPatchType type;
    Array<Vec2> polygon;
    float elevationOffset;
    uint32 materialVariant;
};
```

畑・田んぼは矩形セルではなく、道路・海岸・地形勾配に沿う Polygon として生成する。畝や畦は Polygon 内の方向ベクトルに沿って生成する。

### F. 海岸ルール

水面に近い土地は住宅地にしない。標高と水辺距離から CoastalBand を作る。

- `waterDistance < 24m`: Beach または Seawall
- `24m <= waterDistance < 60m`: 公園、港湾舗装、道路、護岸背後の空地
- 住宅・商業・工業 Parcel は `waterDistance >= 60m`、または Seawall + 幹線道路の背後のみ許可

海沿いの幹線道路は護岸または砂浜とセットで生成し、建物が直接水際に立たないようにする。

### G. 幹線道路と生活道路の街区構造

`DistrictRoads` の集落内部生成を二層に分ける。

- 幹線: 旧街道/県道/国道として settlement 間と中心部を結ぶ。幅広・歩道あり・商業/公共施設が沿う
- 生活道路: 幹線から枝分かれし、短冊状宅地へ接道する。狭幅・側溝あり・外側緑Slopeなし

Parcel は必ずこの道路階層から作る。城下町/宿場町は幹線沿い商業、背後に生活道路と住宅地、外縁に農地という構造を持つ。

### I. シェーダー/写実トーン

Siv3D標準3D描画を維持しつつ、まず以下を導入する。

- Terrain/Road 用のマテリアル色をSRGB前提で統一し、過度な彩度を落とす
- PBR風の albedo/roughness/normal を将来扱えるよう、Asset metadata に `normal_texture`, `roughness_texture` を予約
- 地表と道路は Mipped texture を使い、遠景の単色タイル感を減らす
- 追加シェーダーは最後に薄い color grading / ambient occlusion 風の2D後処理として導入し、描画パイプラインを壊さない


## Canonical Data と派生キャッシュ

### RoadGeometry 共有API

まず `src/road/RoadGeometry.hpp/.cpp` を追加し、道路断面とベジェから派生する幾何情報を一元化する。`RoadRenderer`、`WorldRenderer`、`GameScene`、`ZoneManager` は道路幅や高さを個別計算しない。

Canonical data:

- `RoadEdge.parts`
- `RoadEdge.lanes`
- `RoadEdge.cutoffA/B`
- `RoadEdge.useElevation`
- `RoadNode.attachments`

RoadGeometry の派生API:

```cpp
struct RoadSurfaceFrame
{
    Vec3 position;
    Vec3 tangent;
    Vec3 right;
    float surfaceY;
    float markingY;
    float furnitureBaseY;
};

struct RoadbedRange
{
    float left;
    float right;
    float width;
};

struct RoadFootprintSample
{
    Array<Vec2> polygon;
    RectF bounds;
};
```

- `roadSurfaceY(edge, bezier, world, arc)`
- `roadMarkingY(edge, bezier, world, arc)`
- `roadFurnitureBaseY(edge, bezier, world, arc)`
- `roadbedRange(edge, ft)`
- `drivableRange(edge, ft)`
- `roadFootprint(edge, bezier, marginA, marginB)`
- `distanceToRoadFootprint(point, edge, bezier)`

通常道路の高さは地形面 + `kRoadSurfaceLift`。高架/橋梁だけ `edge.useElevation` でベジェYを使う。標示・家具・地形切削はこのAPIを通じる。

### RoadMarking の所有と保存

RoadMarking は canonical data と派生 data を分ける。

Canonical manual data:

- 手動配置・プレイヤー編集された標示だけを `RoadNetwork::m_manualMarkings` に保存する。
- `RoadBinary` には保存しない。現行 `roads.bin` は `writeGlobal()` が `RoadObject` / `RoadRoute` / `RoadPlan` を順序固定で追記しており、途中に新規ブロックを挟むと互換性と skip 処理が壊れるため。
- `global/road_markings.json` を新設し、手動標示と自動標示の override だけを保存する。欠損時は空配列として扱い、自動標示だけを再生成する。
- 標示追加だけでは `RoadBinary::kVersion` を上げない。RoadPart の canonical layout を変える場合だけ、`RoadPart` record 内に `placement` と `envelopeRole` を `type` の直後へ追加し、`read()` / `readGlobal()` の skip size を同じ phase で更新する。
- `id`, `kind`, `scope(edge/node)`, `edgeId`, `nodeId`, `arcOffset`, `lateralOffset`, `size`, `anglePolicy`, `overrideMaterial`, `autoGenerated=false` を持つ。
- 自動標示をユーザーが移動/削除した場合は、manual override として `overrideMode = Replace | Suppress | Add` を保存する。

Derived auto data:

- 車線線、停止線、横断歩道、矢印、導流帯は `RoadMarkingGenerator` が `RoadEdge/Lane/RoadNode/TrafficControl` から毎回推論する
- 自動標示は保存しない。保存時は manual override だけ保存し、ロード後に再生成する

Renderer cache:

- `RoadRenderer::m_markingCacheByEdge` と `m_markingCacheByNode` の2種類だけを持つ
- `eraseEdgeCaches(edgeId)` は edge cache と edge に紐づく manual marking cache を無効化する
- `eraseNodeCaches(nodeId)` は node cache を無効化する
- 既存 `m_stopLineCache`, `m_crosswalkCache`, `m_laneArrowCache`, `m_laneCache`, `m_nodeCapLaneCache` は廃止または内部移行する

既存描画経路の撤去順:

1. `RoadMarkingGenerator` と `buildRoadMarkingBatches()` を追加し、旧 `buildLaneLineMeshes()` / `buildStopLineMesh()` / `buildCrosswalkMesh()` / `buildLaneArrowMesh()` は private helper としてのみ呼ぶ。
2. `drawEdge()` は `m_laneCache` を参照しない形に変更し、edge scope 標示は `m_markingCacheByEdge` だけから描画する。この時点で `m_laneCache` の draw call は削除する。
3. `drawNodeCap()` は近距離判定だけを残し、node scope 標示は `m_markingCacheByNode` だけから描画する。この時点で `m_stopLineCache` / `m_crosswalkCache` / `m_laneArrowCache` / `m_nodeCapLaneCache` の draw call は削除する。
4. 旧 cache メンバと旧 builder は、新 cache が Release capture で二重描画なしに通った後で削除する。移行期間中も旧 cache を描画経路へ残さない。

生成単位:

- Edge scope: lane line, dashed/solid center line, edge line, mid-block arrows
- Node scope: stop line, crosswalk, intersection arrows, zebra zone

全標示は RoadGeometry の `roadbedRange()` でクリップし、`RoadSurfaceFrame::markingY` に置く。

### RoadPart と沿道反復オブジェクトの責務境界

RoadPart は引き続き「道路所有物の canonical data」。ただし「道路構造幅へ寄与する部品」と「道路が所有する沿道反復部品」を必ず分ける。

- `Strip`: 現行の幅方向帯。Roadbed/Shoulder/Sidewalk/Curb/Gutter/Slope/Guardrail/Wall
- `RepeatAlongEdge`: RoadPart の代表オフセットに沿って、同じ部品を弧長方向へ反復配置する。UtilityPole/StreetLight/RoadsideObject

`RoadPart` の canonical data に以下を追加する。`RoadPartDef` にも同じ既定値を置けるが、RoadGeometry / WorldRenderer / save validator が registry なしで判定できるよう、最終判定は `RoadPart` 本体の値を使う。

```cpp
enum class RoadPartPlacement : uint8
{
    Strip,
    RepeatAlongEdge,
};

enum class RoadPartEnvelopeRole : uint8
{
    Structural,      // totalWidth / node cap / terrain subtraction / parcel exclusion に含める
    RoadOwnedObject, // 道路が所有するが、道路構造幅には含めない
};

struct RoadPart
{
    String defId;
    float offsetA_L;
    float offsetA_R;
    float offsetB_L;
    float offsetB_R;
    BuildState build;
    RoadPartType type;
    RoadPartPlacement placement = RoadPartPlacement::Strip;
    RoadPartEnvelopeRole envelopeRole = RoadPartEnvelopeRole::Structural;
};
```

保存互換の規則:

- `RoadPartType` は既存値を明示固定する。`Roadbed=0, Shoulder=1, Median=2, Sidewalk=3, Gutter=4, Guardrail=5, Wall=6, Curb=7, Slope=8, BikeLane=9` とし、新規 `UtilityPole` / `RoadsideGutter` / `RoadsideObject` は末尾 `10` 以降にだけ追加する。途中挿入は禁止する。
- `RoadPart` canonical layout を変更する phase で `RoadBinary::kVersion` を 14 に上げる。
- `read()` は v13 と v14 を受け付ける。v13 では `placement=Strip`、`envelopeRole=Structural` を補完する。既存 enum 値は固定済みなので `Curb` / `Slope` / `BikeLane` は化けない。
- `write()` は v14 だけを書く。`readGlobal()` の「エッジskip」は v13/v14 の part record size を分岐し、RoadObject/RoadRoute/RoadPlan の追記位置を正しく見つける。
- `RoadPresetStore::partToJson()` / `partFromJson()` は `placement` と `envelopeRole` を保存・復元する。欠損時は v13 と同じく `Strip` / `Structural` で補完する。
- `RoadPartDef` の `spacing_m` / `jitter_m` / `side_policy` / `face` は `defId` に紐づく registry data として保存する。RoadPreset は個別値を複製せず、`defId` と `RoadPart` canonical role を保存する。
- 標示の manual override は引き続き `global/road_markings.json` に保存し、`roads.bin` の追記領域には入れない。

幅計算の規則:

- `RoadEdge::totalWidth()` は段階移行中の互換用として残すが、新規コードからは直接呼ばない。最終的には `RoadGeometry::structuralRange(edge)` を呼ぶ thin wrapper に変える。
- `RoadGeometry::structuralRange(edge)` は `part.build == Built && part.placement == Strip && part.envelopeRole == Structural` だけを見る。
- `RoadGeometry::roadbedRange(edge)` は `part.build == Built && part.type == Roadbed && part.placement == Strip` だけを見る。
- `RoadGeometry::roadOwnedObjectRange(edge)` は `RepeatAlongEdge` の代表オフセットを返すが、terrain subtraction、node cutoff、Parcel exclusion、node cap の幅には使わない。
- `RoadRenderer::buildPartMeshes()` は `Strip` と `RepeatAlongEdge` を分岐する。`RepeatAlongEdge` を従来のstrip meshへ流さない。
- `UtilityPole` / `RoadsideObject` は `RoadEdge.parts` に入れてよいが、`placement=RepeatAlongEdge` かつ `envelopeRole=RoadOwnedObject` を必須にする。
- `RoadsideGutter` は側溝そのものが地面を占有するため `placement=Strip` かつ `envelopeRole=Structural` とする。

Canonical data:

- 道路種別に必要な沿道部品は `RoadEdge.parts` に保存する。例: 生活道路の `RoadsideGutter`, `UtilityPole`
- 個別の橋脚や手動配置の特殊物は既存 `RoadObject` を使う
- 自動反復インスタンスは保存しない。`RoadPart + RoadPartDef + edgeId + seed` から決定的に生成する

RepeatAlongEdge 生成規則:

- `sStart = marginA + cutoffBuffer`
- `sEnd = totalLength - marginB - cutoffBuffer`
- spacing/jitter は `RoadPartDef` に従う
- 左右は RoadPart の offset 符号と `side_policy` で決める
- 交差点・横断歩道・バス停などの exclusion span と衝突する場合はスキップ
- `edge.id`, `part index`, `sample index`, `world seed` から hash を作り、毎回同じ位置に置く

### Parcel / LandPatch の既存データ接続

`Chunk` に以下を追加する。

```cpp
Array<Parcel> parcels;
Array<LandPatch> landPatches;
```

保存:

- 初期実装では `global/parcels_landpatches.json` に保存する。現行 save は道路/地区も global 保存なので、既存 load flow に接続しやすい。
- `meta.json` の `version` は 4 に上げる。version 3 以下または `parcels_landpatches.json` 欠損時は、ロード後に道路/地区/zoneMap から Parcel/LandPatch を再生成する。
- JSON ルートは `{ "version": 1, "parcels": [], "landPatches": [] }` とする。
- `Parcel` は `id`, `chunkX`, `chunkY`, `zone`, `frontageEdgeId`, `frontageStart`, `frontageEnd`, `setback`, `buildingType`, `polygon`, `buildablePolygon`, `representativeCell` を保存する。
- `LandPatch` は `id`, `chunkX`, `chunkY`, `type`, `materialVariant`, `elevationOffset`, `polygon`, `sourceParcelId` を保存する。
- `id` は `stableHash(seed, frontageEdgeId, frontageStartBucket, zone, polygon centroid)` を基準にし、道路編集後も局所変更だけで済むようにする。
- 将来チャンク単位保存に移す場合も、同じ JSON schema を `chunks/{cx}_{cy}/land.json` に分割できるよう、全レコードに chunk 座標を持たせる。

既存 `zoneMap` / `buildingGrid` との関係:

- `zoneMap` は用途ポテンシャルとUI編集用の粗いグリッドとして残す
- `parcels` が建物配置の canonical data になる
- `buildingGrid` は当面の互換レイヤとして残し、Parcel の代表セルに投影する
- 新規配置は Parcel から行い、接道なしの infill 配置は禁止する

ロード順:

1. `terrain.bin` / `roads.bin` / `guide_signs.json` / `districts.json` を現行どおり読む。
2. `applyZonesGlobal()` で zoneMap へ地区用途を反映する。この段階では建物を生成しない。
3. `global/parcels_landpatches.json` が存在すれば `parcels` / `landPatches` を読む。存在しない、または validation 失敗なら道路・地区・zoneMap から再生成する。
4. 全チャンクの `buildingGrid` を一度 clear し、Parcel の `buildablePolygon` と `representativeCell` から互換投影する。
5. `placeInitialBuildings()` はロード経路から外し、legacy save の one-shot migration または明示的な debug fallback でのみ呼ぶ。通常ロードでは呼ばない。
6. 保存済み Parcel を読んだ場合も、道路 footprint との交差、frontageEdgeId の存在、海岸band内住宅を validation し、破綻した局所だけを再生成する。

描画:

- `WorldRenderer` は `LandPatch` を任意多角形メッシュとして描画する
- 建物は `Parcel::buildablePolygon` または `frontageEdgeId + setback` から配置する
- `buildingHitBox()` は Parcel 内建物位置を使い、旧 `buildingGrid` のセル中心前提を段階的に縮小する

道路編集後の更新:

- 道路追加/削除/移動で影響するチャンクを RoadGeometry の footprint bounds から求める
- そのチャンクの Parcel/LandPatch/Building projection を再生成または dirty にする
- 既存のゾーンUIは zoneMap を編集し、次の parcel rebuild で区画へ反映する

### 接道義務と非重複の不変条件

初期生成および自動再生成後、以下を常に満たす。

- 宅地/商業/工業 Parcel は `frontageEdgeId >= 0`
- frontage length は原則 2m 以上
- Parcel polygon は RoadGeometry の道路フットプリントと交差しない
- 建物 footprint は Parcel 内に収まり、道路フットプリントから setback 以上離れる
- 農地/田んぼは農道または生活道路に接する LandPatch として生成する
- 海岸バンド内には住宅 Parcel を生成しない

検証用に `scripts/validate_city_generation.ps1` を追加し、Release capture 後に以下をログ化する。

- 道路/建物交差数
- 接道なし Parcel 数
- RoadMarking の roadbed range 外頂点数
- 海岸バンド内住宅数

検証は最後だけでなく各導入直後に走らせる。

- RoadGeometry 導入直後: 道路面Y、標示Y、terrain subtraction Y の差分最大値、通常道路の浮き量最大値をログ化する。
- RoadMarking 導入直後: 全 marking quad 頂点が `roadbedRange()` 内にあるか、node/edge scope の二重描画数が 0 かをログ化する。
- RoadPart 移行直後: `Structural` 幅と `RoadOwnedObject` offset を分けて出力し、UtilityPole が total footprint を広げていないことを検証する。
- Parcel/LandPatch 導入直後: 接道なし Parcel、道路/建物交差、海岸band内住宅、Parcel 投影後 buildingGrid 件数をログ化する。


### Dirty / Invalidation ルール

RoadGeometry は値を保持しない純粋な派生APIにする。キャッシュを持つのは呼び出し側だけとし、無効化条件を以下に固定する。

- `RoadRenderer::eraseEdgeCaches(edgeId)`: RoadPart/Lane/Bezier/edgeState/useElevation/texture/marking manual override が変わったとき。部品メッシュ、エッジ標示、RepeatAlongEdge部品、標識、案内標識を消す。
- `RoadRenderer::eraseNodeCaches(nodeId)`: attachment/cutoff/trafficControl/signal/manual node marking が変わったとき。ノードキャップ、ノード標示、信号取付、交差点導流帯を消す。
- `WorldRenderer::invalidateTerrainForEdges/Nodes`: RoadGeometry の `roadFootprint()` bounds が変わる変更、または通常道路高さ/高架状態が変わる変更で呼ぶ。
- `GameScene::markParcelRegionDirty(bounds)`: 道路 footprint bounds、海岸 band、zoneMap が変わった範囲の Parcel/LandPatch/Building projection を再生成対象にする。
- `World` heightMap が再生成された場合は、道路レンダ・地形subtraction・Parcel/LandPatch を全dirtyにする。

このルールにより、道路幅・高さ・標示クリップを複数箇所で再計算しても同じAPIに集約され、浮き/はみ出し/重なりの再発を防ぐ。

### Parcel 切り出しアルゴリズム

Parcel生成は道路frontageから行う。

1. 対象 settlement 内の LocalRoad/Arterial edge を弧長8〜14m刻みでサンプリングする。
2. 各サンプルで RoadGeometry の roadbed/total footprint 外端から外側法線を作る。
3. ZoneType と RoadType から frontage width と depth を決める。
   - LocalRoad + LowResidential: frontage 7〜11m, depth 14〜24m
   - LocalRoad + Residential: frontage 9〜14m, depth 18〜30m
   - Arterial + Commercial: frontage 18〜36m, depth 24〜48m
   - Industrial: frontage 24〜48m, depth 32〜64m
   - Agriculture: frontage 24〜80m, depth 40〜120m
4. 矩形候補を作り、道路 footprint と交差する部分を offset で押し戻す。
5. 隣接道路/海岸band/急斜面/既存Parcelと交差する場合は polygon clipping で削る。面積が閾値未満なら破棄する。
6. `frontageEdgeId`, `frontageStart`, `frontageEnd` を持つ Parcel として登録する。
7. 建物は `buildablePolygon = polygon inset(setback)` の中で、道路に正面を向けて配置する。
8. チャンク境界をまたぐ Parcel は保存上は centroid chunk に置き、描画時に polygon bounds で関係チャンクへ配る。後のチャンク分割保存時もIDは変えない。

既存移行:

- Phase 1: 既存 `buildingGrid` へ投影しつつ、接道なし infill を無効化する。
- Phase 2: 選択/パネル/当たり判定を Parcel ID に対応させる。
- Phase 3: `buildingGrid` は互換保存/古いUI用のビューに縮退する。
## 実装順序

1. `scripts/validate_city_generation.ps1` とゲーム側 validation 出力口を先に追加し、現状の違反数を baseline として出す。
2. `RoadGeometry` 共有APIを追加し、道路面Y・標示Y・Roadbed範囲・Structural footprintを一元化する。ここで浮き量と footprint を検証する。
3. 通常道路の高さを `RoadGeometry` 経由にし、地形切削と道路/標示/家具の接地を同じ高さ規約に統一する。
4. `RoadMarking` データ構造、`global/road_markings.json`、`RoadMarkingGenerator` を追加し、横断歩道・停止線・車線線を統合する。`drawEdge()` / `drawNodeCap()` の旧 cache draw call はこの phase 内で止める。
5. 生活道路断面から `Slope` を外し、`Curb/Gutter/RoadsideGutter` と `UtilityPole` を RoadPart として追加する。この phase で `RoadPartType` 明示値、`RoadPart` canonical layout、`RoadBinary` v14 読み書き、`RoadPresetStore` JSON 往復を同時に更新し、`RoadPartEnvelopeRole` により UtilityPole は道路所有だが構造幅に含めない。
6. `buildStreetFurnitureBatches()` を撤去し、RepeatAlongEdge RoadPart 描画へ移行する。
7. `Parcel` / `LandPatch` を `Chunk` と `global/parcels_landpatches.json` に追加し、ロード順を Parcel canonical に変更する。`buildingGrid` は clear 後に Parcel から互換投影する。
8. 海岸バンドと砂浜/護岸 LandPatch を追加し、海岸近傍住宅を生成不可にする。
9. CC0素材を取得し、`App/assets/licenses/THIRD_PARTY_ASSETS.md` に記録してTOML/Textureへ紐付ける。
10. Release build/test/capture、コード込みレビュー、実レンダレビューを回す。
## PASS基準

- 道路・道路標示・道路沿い設備が同じRoadPart/RoadMarkingライフサイクルで管理されている。
- 通常道路が地面から浮かず、標示が道路外へはみ出さない。
- 横断歩道の向きが道路横断方向である。
- 生活道路の外側に不要な緑Slopeがない。
- 建物・土地が道路に重ならず、宅地/商業地/農地が道路に接している。
- 海岸に住宅が直接置かれず、砂浜または護岸の緩衝帯がある。
- 外部素材のライセンスがファイルに記録されている。
- 実ゲームレンダで、低ポリであっても地方都市/郊外の道路階層と土地利用が読み取れる。
