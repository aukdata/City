# 木のチャンク表示とLOD切り替えが遅い原因

2026-09-18 調査。対象は現在の非同期地形・景観描画経路。動作変更は行わず、コードの追跡と自動ナビゲーション計測を実施した。

## 結論

木の元形状は共有済みだが、GPUで描く木は個体ごとに頂点を複製・変形してチャンクのメッシュに結合している。近景LODが未準備だと、この大量の頂点生成に加え、地形と景観全体の再生成・GPU転送まで待つ。そのため「数種類の共有モデルからLODを選ぶだけ」にはなっていない。

準備済みのLOD選択は距離判定だけで軽い。共有したGPUメッシュと個体の配置情報に分ければ、LOD変更に伴う大量の頂点再生成・再転送は避けられる。ただし初回の配置判定、個体情報の更新、描画そのものの負荷は残る。

## コードで確認した原因

1. **共有しているのはCPU上の原型。** `WorldRenderer_Buildings.cpp::appendLandscapeTree()` は `static std::array<TreeGeometry::Geometry,16>` を一度作る。広葉樹/針葉樹 × 4変種 × 公園用/森林用の16種で、低木の原型は別に1つある。しかし毎木・毎部位で `MeshData mesh=*entry.second` を実行し、拡大縮小・回転・平行移動した全頂点とインデックスを `appendMeshData()` で再コピーする。近景の低木にも同じ複製がある。木のモデルファイルを毎回読み込む経路ではない。
2. **LODの準備が地形再生成を引き起こす。** `WorldRenderer_Streaming.cpp::drawChunk()` は `needsTreeDetails` を `terrainDirty` に含める。起動するジョブは常に `buildTerrainMeshData()`、次に `buildLandscapeMeshData()` を実行する。景観側では道路・河川等の除外領域、全敷地、公園、自然林を作り直す。配置だけを再利用するキャッシュはこの経路にない。
3. **初回は地形だけ先に表示し、木を一括公開する。** チャンクの地形キャッシュがない場合は道路で切り抜く前の簡易地形を即時表示する。景観キャッシュはジョブの全地形・全景観のGPU転送が終わった時点で初めて公開する。近い新規チャンクでは詳細な木の生成が終わるまで、遠景の樹冠だけを先に公開する段階もない。既存チャンクを詳細化する間は、従来の遠景メッシュが残る。
4. **処理枠と転送の分割で待ち時間が積み上がる。** 未完了ジョブは最大2件。この枠はCPU生成終了後もGPU転送完了まで占有する。`uploadCompletedTerrain()` は1フレームに1ジョブ、約2msを目安に転送する。各メッシュ生成は途中で中断できず、2msを超えることもある。新規ジョブは近傍優先だが、開始済みジョブをカメラから遠ざかったという理由で取り消す処理はない。
5. **描画より準備の範囲が広く、離れると捨てる。** `TreeGeometry.hpp` では256mタイルの境界まで600m以内を詳細表示、チャンク境界まで1100m以内を準備対象、1500mまで保持する。準備は1024mチャンク全体に対する真偽値であり、表示するタイルだけを生成する方式ではない。1500mを越えると `trimDistantTreeDetails()` が詳細バッチを破棄するため、戻れば再生成になる。

`drawLandscapeBatch()` は準備済みバッチを距離で選ぶだけで、ここに秒単位の処理はない。遅いのは未準備LODの用意と公開待ちである。

## 実測

開始時点から存在していた計測用バイナリ `artifacts/tree_streaming_20260918/bin/City.TreeProfile.exe` と、同じく既存の `LandscapeBuildStats` / `[TreeStreaming]` 計測を利用。Release、シード42、新規生成、通常設定の森林密度95%、`--benchmark-navigation` の6段階を自動実行した。既存バイナリを一時的に `App/City.TreeAudit.exe` にコピーして資源の揃う場所から実行し、終了後に一時コピーを削除した。今回ソースの編集・再ビルドは行っていない。

正常終了、6段階完走、2,837フレームを確認。完成したジョブは詳細23件、遠景のみ46件。ジョブ数は再生成を含み、ユニークなチャンク数ではない。警告ログはなく、森林設定は実行前後でバイト一致した。

| 詳細LODジョブ23件の指標 | 平均 | 中央値 | 最大 |
|---|---:|---:|---:|
| CPU側生成の経過時間 | 1,542.54 ms | 1,186.97 ms | 3,839.81 ms |
| うち地形生成 | 541.56 ms | 373.06 ms | 2,129.95 ms |
| うち除外領域の準備 | 8.67 ms | 5.60 ms | 35.65 ms |
| うち敷地・公園等の景観生成 | 574.63 ms | 508.43 ms | 1,716.26 ms |
| うち自然林生成 | 416.12 ms | 9.17 ms | 3,834.99 ms |
| GPUメッシュ作成・転送に費やしたCPU側経過時間の合計 | 69.83 ms | 52.03 ms | 191.19 ms |
| 転送を実施したフレーム数 | 23.13 | 22 | 36 |
| 景観の頂点数 | 3,767,376 | 2,720,356 | 15,580,688 |

内訳の最大値はそれぞれ別のジョブであり、足し合わせない。時間は `Stopwatch` による経過時間で、CPUの稼働時間やGPUタイムスタンプではない。転送フレーム数は待ちを含む表示遅延の総フレーム数ではない。仮に連続して60fpsで転送する場合でも平均23.13フレームは約0.39秒分であり、実際には生成・処理枠待ち・他ジョブの転送待ちが加わる。

具体例:

- 森林チャンク `(17,46)` は生成3,839.81msのうち自然林が3,834.99ms。景観15,580,688頂点・14,373,600三角形、転送191.19msを35フレームに分割した。この例では木の大量生成がほぼ全てを占める。
- 市街地を含む `(20,47)` は地形1,849.28ms、敷地・公園等1,716.26ms、自然林7.61ms。自然林だけ軽量化しても地形と敷地の再生成待ちが残る。
- 同じ `(17,45)` の遠景生成は15.27ms、詳細化では2,610.30msだった。全ジョブの平均を単純比較するより、同じチャンクの詳細化で負荷が増えることが分かる。
- 6チャンクでは詳細ジョブの完成が各2回記録されていた。カメラ移動後の再生成が発生することもログで確認した。ただし現在のログには起動理由がないため、個々の再生成が保持距離による破棄か別の無効化かは断定しない。

参考として、開始時点に存在した森林密度95→0の比較も確認した。密度0でも公園・敷地内の木と高山植生は残り、地形・景観処理も残るため、「木を全て無効にした対照実験」とは扱えない。

## 改善の方向

優先順位は次のとおり。

1. 木の種類・LODごとのGPUメッシュを共有し、個体ごとには位置・回転・大きさ・色などを保持する。個体ごとの全頂点コピーをやめる。描画要求が一本ごとに増えないよう、種類・LOD・タイル単位でまとめて描画する。
2. 木の配置とLODの選択を分離し、地形や道路が変わらない限り配置・除外判定を再利用する。木のLOD変更で地形や敷地を作り直さない。
3. 新規チャンクでは遠景の木を先に公開し、詳細化を独立して進める。準備対象と処理枠も地形から分離し、必要なタイルを近い順に処理する。
4. 距離で解放する対象を個体の配置情報や描画対象リスト中心に見直し、少数の共通モデルは保持する。

既存の `VehicleInstanceBatch.hpp` は、不変の頂点と個体ごとの変換を分ける設計の参考になる。ただし無テクスチャ遠景車両専用で、木の葉のUV・葉用シェーダー・影にも対応する必要があり、そのまま差し替えるものではない。

生成枠や2ms予算だけを増やすとメインフレームやメモリ負荷へ移るため、モデル共有と再生成範囲の縮小を先に検討する。改善幅の確定には改修後の同条件計測が必要。
