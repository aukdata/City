# ゲームプレイ軽量化（2026-10-31）

## 計測条件

- i7-14700KF / Radeon RX 9070 XT / 80GB、Release、`--seed 42 --new --uncapped`、既定ウィンドウ。
- `--playtest-commands` の `benchmark_view` で街の中心を固定視点にし、8時から交通を動かして各視点で240フレーム待機後に600フレームを集計。近景 220m・速度1、中景 650m・速度2、広域 3000m・速度4。
- 比較は 8dd9313（変更前）と 202c5ba（変更後）の実行ファイルを交互に2回ずつ。値はフレーム間隔の平均 / P95（ms）。

| 視点 | 変更前 | 変更後 |
|---|---|---|
| 近景 | 24.7–25.1 / 36.5 | 16.3–16.8 / 21.5–22.4 |
| 中景 | 31.0–32.2 / 43.2–45.1 | 21.5–22.1 / 29.6–31.0 |
| 広域 | 34.5–35.1 / 45.4–46.3 | 18.6–19.9 / 22.6–24.3 |

- 描画CPU（renderMs）は近景 20.2→12.6、中景 25.6→16.7、広域 28.4→13.9。GPU時間は 3〜7ms で変更前後とも律速ではない。
- メモリ（RSS）は最大 2.8〜2.9GB で差は計測のばらつき内。新規生成のロード時間は 92〜93s → 89〜91s。
- streaming 計測（720サンプル、時間停止）はフレーム間隔 平均/P95 29.7/79.9 → 16.7/26.8ms。ただし変更前の回は外部のGPU負荷が重なった可能性があり、参考値。

## 特定したボトルネック（VS Standard Collector のCPUサンプリング、広域）

1. 川の水面メッシュの再構築（全サンプルの約29%）。0.1秒ごとに各チャンクで、全頂点が近傍の河道・河川区間を毎回探索していた。
2. 河道の流量計算（約7%）。毎ステップ全河道で exp/expm1 を計算していた。
3. 建物描画で `ModelObject::draw` が部品ごとに TextureAsset を名前で検索（約4%）。
4. 車両の姿勢計算で、全車両が毎フレーム道路のベジェ弧長表を作り直していた（約4%）。
5. 計画道路のワイヤー描画が、計画道路が無くても空間検索と交差点半径の計算をしていた（約3%）。

## 変更と同一性の確認

- 水面メッシュ：河道候補と最寄り区間を半格子ごとにチャンク単位でキャッシュ。読み取った河道の水位と地面が前回とビット単位で同じなら再構築を省略（更新枠は従来どおり消費し、他チャンクの更新フレームは変えない）。`SourceWater.CachedLatticeMatchesDirect` でキャッシュ有無・省略時のメッシュがビット一致することを確認。
- 流量計算：減衰係数をステップ幅ごとに一度だけ計算。全河道の水量・流量がビット単位で不変になった後は、台帳の加算だけを同じ順序で行う。`SourceWater.SettledStepsMatchFullSteps` で完全計算との保存データのビット一致を確認。
- 建物：材質ごとに読み込めたテクスチャを保持し、`ModelObject::draw` と同じ描画を発行。`ModelLod.TextureCacheMatchesNativeDraw` でGPU描画結果のピクセル一致を確認（描画方法を誤らせた版では失敗することも確認）。
- 車両：辺ごとに曲線を保持し、両端ノード位置と制御点が一致する場合だけ再利用（`getBezier()` と同値）。
- ワイヤー：計画中の辺が1本も無い場合に処理を省略（描画対象が無い場合だけ）。

## テスト

- 全 513 件中 512 件成功。失敗の `StreetDetail.FacadeAttachments`（入口設備の高さ）は変更前の 8dd9313 でも同じ理由で失敗する既存の問題。

## 残る主な負荷

- Siv3D の描画呼び出しごとのメッシュ参照・バインド（中景で約10%）、道路描画、車両シミュレーション、歩行者更新、デバッグログ文字の毎フレーム組版。描画順や結果を変えずに減らせる方法は未確定。
- 河道は閉じた末端に水が溜まり続けるため、実プレイでは水位が完全な定常に達しにくく、水面メッシュの再構築省略は約2割にとどまる。
